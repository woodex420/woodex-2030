# WOODEX OS — release report, 17 November 2026

The first report in the form of document 10 §9 (list line T-170). Its ten headings are that document's ten
points; `scripts/verify-acceptance.mjs` refuses a release report without them.

**What went out, and on whose word.** On 17 November the owner lifted the holds: "this is not private data, this
is Woodex data"; "unfreeze, unblock, everything, to start production-ready deployment" (decision DL-022). Under
that word:

| | What | State |
|---|---|---|
| 1 | The admin is Furniture-only, holds times in UTC, and carries Woodex's real catalogue: 170 products, as drafts | In the code; live on the hosted workspace `woodex-os.vercel.app` since 09:02 UTC |
| 2 | The React shop's database: Supabase's Data API closed, catalogue migration 019 applied, three rows of the migration ledger corrected | Done and read back (DL-024) |
| 3 | The acceptance scenarios, the browser flows, the gates, a sheet per module and the defect register, kept true by a check in CI | In the code (document 16) |
| 4 | Pull request #36 merged into `main`, from which Vercel rebuilds the React shop and the hosted workspace | **Done at 10:22:38 UTC: merge commit `88ec4cc`**, after the owner's "start" of 10:20 UTC. Vercel rebuilt both sites; asked from outside at 10:31 UTC, both answer as they should (§3) |

**What did not go out.** No product was published anywhere. No customer, lead or order was moved. Nothing was
installed on Hostinger. The React shop still sells its 148 sample products: replacing them is three actions in
the old dashboard, which needs the owner's sign-in (line T-091).

**What the merge carried into the React shop.** The branch held more than this round's work. Since 16 November
it contained the Laravel branch (merge `9194028`), and with it the work done between 11 and 13 November on the
shop, its API, its dashboard and the root of the repository (thirteen commits, by `git log`), plus two
corrections of 16 November (`208ab02`, `4277e0f`). None of that was live while `main` stood at `4363530`; it is
live since the merge. Compared file by file, `4363530` against `88ec4cc`, in `apps/` and at the root:

| What | For a visitor, or for staff |
|---|---|
| The Products menu and the category lists are built from one category file, shared with the admin (`platform/resources/data/commerce-taxonomy.json`) | The menu is a plain two-column list: its two picture tiles are gone and its headings are links. Three entries were added under "Seating & More": Home Office, Acoustic Furniture, Collaborative Furniture. A heading such as "Office Tables" now lists the products of all its sub-categories. The Series menu holds the same five series |
| Two optional connections to the Laravel admin, for categories and for pictures | Off. The shop asks its own API, is told "disabled", and asks again ten minutes later. Nothing is fetched from the admin |
| An optional second destination for the enquiry form and the basket request: the Laravel API, with a verification box | Off: the site is built for the old destination, as long as the Vercel project holds the four settings read on 17 November and no other. Enquiries and quotation requests go where they went before, to the shop's own API and database |
| The old dashboard: its side menu and product pickers | The corrections of 13 November (`c9e7096`) |
| Files for Hostinger at the root of the repository (`.htaccess`, `index.php`) and two Hostinger workflows | Not used by Vercel. The workflows start only on the other branch or by hand. Whether Hostinger itself fetches `main` cannot be seen from here |

**This table was missing from the report before the merge, and should have been in it**: the report named the
merge and the rebuild, not what the rebuilt shop would do differently. It is defect D-014, and the owner's word
on the shop as rebuilt is asked in line T-026. What stood behind those commits at the moment of the merge: the
shop's gate — build, type check, the API's tests, and the browser journeys, one of them from the shop's enquiry
form into the CRM — passed on the branch and again on the merge commit, and the outside check passed after it
(§3). The way back is in §7.

## 7. Backup/restore status

**No backup was taken before the database was changed, and none has been restored.** Whether the Supabase plan
keeps backups was not checked. This is defect D-011 and line T-187. What stands in for it today:

| Change | The way back |
|---|---|
| Privileges taken from the API roles | The four `GRANT` lines at the head of `deploy/supabase/2026-11-17-close-data-api.sql` |
| Migration 019 | `scripts/migrations/rollback/019_catalogue.rollback.sql`, and the removal of ledger row 19 |
| Ledger rows 16 to 18 | Their old values: `016_support` with `sha256:696ffe6e3cfc024b`; `017_credentials` and `018_throttle`, each with `sha256:` before the checksum it has now |
| The hosted workspace | The earlier deployment, kept by Vercel |
| The React shop as rebuilt by the merge | Its earlier build, from `4363530`, is kept by Vercel and can be put back there ("Promote" or "Rollback"). Migration 019 does not stand in the way: that build ran on the migrated database from 09:00 to 10:26 UTC, and the outside check passed 12 of 12 on it (run 44057537127). Putting back `main` itself is a revert of `88ec4cc` |
| The data itself | The 148 products are those of the seed file `apps/api/seed-data.json`; nothing else of value is in the database yet |

That stops being enough with the first real order. The Laravel admin holds no real record, so it has nothing to
back up yet; its backups are proven on Hostinger (T-137).
