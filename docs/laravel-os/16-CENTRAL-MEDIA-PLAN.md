# Central media management — implementation direction

## Owner requirement

Website → Media is the master library, not a Soon destination. Organize product photography separately from banners, categories, collections and general website assets. Product upload/selection/replacement must use this master library, and explicitly connected published storefront uses must receive image replacements without re-entering URLs. Keep CRM/conversation/customer attachments outside this library.

## Current implementation boundary

The admin Media screen is now independently accessible with `website.edit`, while Pages & builder and other unfinished Website screens remain disabled. Upload folders, folder filtering and metadata organization are available. Changing a folder classifies the asset without breaking its physical path or existing references. Admin thumbnails use a permission-checked, private, non-cached image endpoint independent of the public Website module. Deletion checks both static page usage and native CMS media references.

Product editor currently **copies** selected website media into immutable private product media. That protects saved revisions but is NOT master-library synchronization. The existing React storefront uses a separate catalogue/image projection. No live synchronization or complete master-media implementation is claimed by the current slice.

## Next implementation slices

1. **Stable asset identity and immutable versions.** Add an asset table and version records containing disk/path/hash/MIME/bytes/dimensions. Retain originals and historical versions. Use adapters to index existing website and private product files without moving/deleting them; idempotent imports, no fabricated media. Private catalogue assets must not become public merely because they are indexed.
2. **Usage records.** Record asset/consumer/slot/publication/version explicitly for product primary/gallery, variant images, categories, series, CMS blocks, static site files and storefront catalogue. Show actual uses before replace/delete; cover references embedded in builder JSON/URLs as well as numeric IDs. Do not rely only on a filename stem or raw JSON substring.
3. **Product master integration.** Upload through the master service, select an asset ID in the product editor, and pin saved revisions to immutable asset versions. Existing private ProductMedia IDs remain valid during migration. Shared-asset replacement must clearly distinguish “replace only this product slot” from “replace all connected live uses”. Require catalog management plus website publishing authorization where applicable. Reset affected product draft review without silently rewriting historical revisions.
4. **Optimization.** Decode/validate actual raster content, cap pixels/bytes, strip unneeded metadata, retain source, generate bounded WebP/AVIF and responsive derivatives where supported; report actual original/output sizes. Never relabel an unconverted file or claim an unavailable encoder succeeded. Preserve transparent images, aspect ratios, alt text and crop intent.
5. **Publishing/sync.** Asset-version events plus durable outbox jobs update explicitly authorized live projections, with versioned URLs/cache invalidation, retries and visible pending/synced/failed states. The separate React storefront needs an authenticated projection contract and permanent reachable origin/storage, not a sandbox URL or local filesystem assumption. Avoid turning on the entire Website module as a shortcut. Replacement confirmation must list affected live uses; rollback selects the prior immutable version.
6. **Acceptance.** Verify upload → master → product editor → saved preview → authorized live projection; cross-session refresh; replace-one/all; old revision retention; cache freshness; failed-sync retry; optimized derivatives; RBAC; traversal/unsupported files; deletion protection; no exposure of CRM/private drafts; desktop/mobile layouts.

## Reuse implementation — owner clarification, 11 November 2026

This section supersedes the earlier implementation-boundary paragraph. The owner clarified: **upgrade the existing Laravel Media library, preserve its media, and connect the React storefront; do not replace the library with a parallel product-media UI.**

### Available workflow

- `Website → Media` remains the existing `website_media`/Livewire library. Its upload, metadata, alt-text and legacy page behavior remain. Supporting master/version/source/usage tables retain bytes and product revision references behind that library; they are not a second management screen.
- **Import existing React images** indexes actual raster files in `CATALOGUE_SOURCE_IMAGE_ROOT` into the same library, keeping the `/img/filename` source key. It never overwrites React source files or publishes a replacement. Product keys from the checked-in source catalogue receive `website/products`; other raster images receive `website/storefront`. Existing custom folders are not reassigned. Duplicate original filenames with identical bytes remain independently addressable.
- **Replace / reuse** opens a confirmation dialog with upload or existing-library selection. Source-catalogue product names are shown as **snapshot references, not a live usage audit**. A library replacement updates that media identity and native CMS uses by ID; static legacy HTML is not rewritten. Existing product revisions remain pinned. For one product slot, use the product editor's replacement action.
- **Also replace all React uses of /img/…** explicitly publishes that key's version. `website.edit` is required for replacement, plus `website.publish` for React publication. Confirmation and stale-dialog checks run server-side. The public manifest contains only explicitly published keys/versions, never the whole library, CRM attachments or private draft product images.
- **Restore React original** withdraws the mapping. The React frontend restores its bundled/original `/img/…` reference on the next successful refresh. No library, original or retained file is deleted.
- **Optimize** reuses `ImportLegacyMedia`'s existing bounded1600px/WebP-quality82 encoder. It changes the library only when output is smaller, retains the original, and reports actual sizes. Missing GD/WebP support or no savings leaves bytes unchanged. React publication remains a separate explicit replacement confirmation. This is not a full AVIF/responsive-derivative pipeline.
- Product uploads, builder uploads and Media uploads register private retained masters. Selecting a website image in the product editor links the master version while keeping compatible private `ProductMedia` references. Saved product revisions record immutable version/slot uses; a later library replacement never rewrites historical product content. `media:index-masters` non-destructively indexes older website/product media and revisions; reports unavailable sources and exits nonzero rather than inventing assets.

### React connection and deployment

1. Deploy additive Laravel migrations (normal `artisan migrate --force`, never reset). Ensure persistent public/private storage and the real existing React source-image directory are installed. Import existing React images using the Media screen. Do not assume the screenshot's older138media are present in a fresh preview database.
2. Deploy the React/API changes. Set the API's `NATIVE_CATALOGUE_ORIGIN` to the **permanent HTTPS Laravel origin**, with no path, user info or query, and opt in using `NATIVE_MEDIA_SYNC=1`. Media sync is independently OFF by default; do not turn on the entire Website module. Never configure a sandbox as a permanent origin. No production settings have been changed by this slice.
3. The browser uses same-origin `/api/v1/media` and versioned image routes. The Node bridge only forwards these public read-only paths with bounded response size/timeout, no redirects, cookies or staff credentials. Anonymous routing is explicitly allowlisted only for the manifest/numeric image paths; neighboring private paths still require sign-in.
4. React polls every15seconds and on focus. Mappings apply to mounted/new DOM `img`, `picture/source srcset`, and inline background URLs using `/img/…`; originals are retained for disabled rollback and image-load-error fallback. Transient manifest outages keep last known good mappings. This is near-real-time pull sync, **not an acknowledged push-delivery system**. Background tabs may throttle polls.
5. Remote external images, CSS-file background URLs, SVGs, arbitrary upload URLs, legacy static-page rewriting, per-page React slot overrides and live product-price/checkout cutover remain outside this integration. A shared React key replaces every use of that key; use product-slot replacement for an isolated native product change. Source references are a snapshot until a full cross-app usage graph exists.
